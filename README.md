## 3. Running the App

### Two-process run (recommended)

**Terminal 1 — start the backend**

```bash
cd backend
uvicorn app.main:app --reload --port 8000
```

The API is now available at `http://127.0.0.1:8000`.  
Interactive docs: `http://127.0.0.1:8000/docs`

**Terminal 2 — serve the frontend**

Use any static file server. With Python's built-in server:

```bash
cd frontend
python -m http.server 5500
```

Then open `http://127.0.0.1:5500` in your browser.

> The backend's CORS configuration explicitly allows `http://127.0.0.1:5500`
> and `http://localhost:5500`. If you use a different port, add it to
> `FRONTEND_ORIGINS` in `backend/app/main.py`.

### Seed demo data & run the benchmark

```bash
# From the project root (with the venv active)
cd backend
python ../seed.py
```

This inserts a demo user + project + 10 tasks, then prints and saves
comparison counts to `results/benchmark_results.txt`.

### Run the algorithm checks

```bash
# From the project root (with the venv active)
python check_algorithms.py
```

Expected output: one `PASS:` line for every case, no `FAIL:` lines.

## 4. Database Schema

SQLite file: `backend/taskflow.db` (created automatically on first run).

### `users`

| Column | Type    | Constraints              |
|--------|---------|--------------------------|
| id     | INTEGER | PRIMARY KEY              |
| name   | TEXT    | NOT NULL                 |
| email  | TEXT    | NOT NULL, UNIQUE         |

### `projects`

| Column      | Type    | Constraints                        |
|-------------|---------|------------------------------------|
| id          | INTEGER | PRIMARY KEY                        |
| name        | TEXT    | NOT NULL                           |
| description | TEXT    | nullable                           |
| owner_id    | INTEGER | NOT NULL, FK → users.id ON DELETE CASCADE |

### `tasks`

| Column      | Type    | Constraints                                              |
|-------------|---------|----------------------------------------------------------|
| id          | INTEGER | PRIMARY KEY                                              |
| title       | TEXT    | NOT NULL                                                 |
| description | TEXT    | nullable                                                 |
| priority    | TEXT    | NOT NULL, CHECK IN ('low','medium','high'), default 'medium' |
| due_date    | TEXT    | nullable (stores raw text, e.g. "next friday")           |
| status      | TEXT    | NOT NULL, default 'todo'                                 |
| project_id  | INTEGER | NOT NULL, FK → projects.id ON DELETE CASCADE             |

**Relationships**

- `User` → `Project`: one-to-many via `owner_id`; `User.projects` / `Project.owner`
- `Project` → `Task`: one-to-many via `project_id`; `Project.tasks` / `Task.project`

### Sorted List (Section 2)

#### `GET /tasks?sort=priority` — Tasks sorted by priority via `insertion_sort`

The endpoint fetches rows from the DB, maps priority to a numeric rank
(low=1, medium=2, high=3), calls `insertion_sort(records, "_priority_rank")`,
strips the helper key, and returns the sorted list — no `ORDER BY`, no
Python built-in sort.

```json
// Response 200
[
  { "id": 5, "title": "Nice-to-have feature", "priority": "low", ... },
  { "id": 2, "title": "Review PR",            "priority": "medium", ... },
  { "id": 1, "title": "Fix crash in prod",    "priority": "high", ... }
]
```

### Search (Section 2)

#### `GET /tasks/search?title=<exact>&algo=binary|linear`

Builds an in-memory index from real DB rows, sorts with `insertion_sort`
if `algo=binary`, then calls the appropriate search function.

```
GET /tasks/search?title=Fix+inventory+sync+bug&algo=binary
GET /tasks/search?title=Fix+inventory+sync+bug&algo=linear&project_id=1
```

```json
// Response 200
{ "id": 1, "title": "Fix inventory sync bug", "priority": "high", ... }

// Response 404
{ "detail": "No task with title 'Nonexistent' found." }
```

## 6. Algorithms — Complexity Write-Up & Benchmark

### Function signatures

```python
insertion_sort(records: list, key: str) -> None
binary_search(sorted_records: list, target_value, key: str) -> int   # index or -1
linear_search(records: list, target_value, key: str) -> int          # index or -1
```

### Time complexity

| Algorithm       | Best case | Worst case  | Notes                              |
|-----------------|-----------|-------------|------------------------------------|
| `insertion_sort`| O(n)      | O(n²)       | Best when input is already sorted  |
| `binary_search` | O(1)      | O(log n)    | Requires sorted input              |
| `linear_search` | O(1)      | O(n)        | Works on unsorted input            |

### Benchmark results (comparison counts)

Run `python seed.py` from the project root to reproduce these numbers.
The counting wrappers (`insertion_sort_count`, `binary_search_count`,
`linear_search_count`) instrument the exact same logic that powers the
endpoints — not a separate sample.

| Size  | InsSort comparisons | BinSearch comparisons | LinSearch comparisons |
|-------|--------------------:|----------------------:|----------------------:|
| 10    |                ~25  |                    ~6 |             up to 10  |
| 500   |             ~62,500 |                   ~18 |            up to 500  |
| 3,000 |          ~4,500,000 |                   ~24 |          up to 3,000  |

*(Exact counts vary with random data; the order-of-magnitude ratios are stable.)*

### Sort-first trade-off analysis

At n = 3,000, `insertion_sort` costs roughly 4.5 million comparisons — a one-time
O(n²) payment. After that, every `binary_search` costs at most ~24 comparisons
(O(log n)), roughly 125× cheaper than a linear scan at that size.

For TaskFlow's usage pattern — engineers view and sort their task board many
times a day but add or rename tasks infrequently — the sort-first strategy
is worth it. The single sorting cost is amortised across dozens of binary
searches during the day. By contrast, `linear_search` on the unsorted index
costs up to 3,000 comparisons per search query, making it noticeably slower
at scale even though it avoids the upfront sort. The data confirms: sort once,
search fast.

## 7. AI Quick-Add — Prompting Rationale & Worked Examples

### Prompting technique: Zero-shot

The `quick_add_parser.py` system message gives a complete, self-contained
specification of the extraction rules (priority keyword groups, date-phrase
precedence, title-stripping logic) without embedding any worked examples
inside the prompt itself. This is **zero-shot prompting**.

**Why zero-shot?**  
The parsing rules are fully deterministic and enumerable. Embedding worked
examples (few-shot) would increase token usage on every call without
improving reliability — a rule-based mock always follows its rules exactly.
For a real LLM upgrade, zero-shot keeps the prompt short and the system
message maintainable: changing one rule means editing one sentence, not
updating multiple examples. Chain-of-thought was not needed because the
rules have no ambiguous reasoning steps that benefit from an explicit
scratchpad.

---

### Worked examples

Apply the algorithm from `quick_add_parser.py → parse_task_description()`
exactly to verify these by inspection.

---

**Example 1**

Input: `"This is urgent, mark it ASAP please"`

| Field          | Value                                   | Reasoning |
|----------------|-----------------------------------------|-----------|
| `priority`     | `"high"`                                | "urgent" matches group (i) first |
| `due_date_hint`| `null`                                  | No date keyword present |
| `title`        | `"This is , mark it please"`            | "urgent" and "ASAP" both stripped (all group-i keywords); trimmed |

```json
{ "title": "This is , mark it please", "priority": "high", "due_date_hint": null }
```

---

**Example 2**

Input: `"   "` (whitespace only)

| Field          | Value           | Reasoning |
|----------------|-----------------|-----------|
| `priority`     | `"medium"`      | No keyword matched |
| `due_date_hint`| `null`          | No date keyword |
| `title`        | `"Untitled task"`| Strip result is empty → fallback placeholder |

```json
{ "title": "Untitled task", "priority": "medium", "due_date_hint": null }
```

---

**Example 3**

Input: `"Finish the report next Friday, it's urgent"`

| Field          | Value                      | Reasoning |
|----------------|----------------------------|-----------|
| `priority`     | `"high"`                   | "urgent" matches group (i) |
| `due_date_hint`| `"next friday"`            | "next friday" matched as whole two-word phrase before bare-weekday check |
| `title`        | `"Finish the report , it's"`| "next Friday" removed as one span; "urgent" stripped; trimmed |

```json
{ "title": "Finish the report , it's", "priority": "high", "due_date_hint": "next friday" }
```
